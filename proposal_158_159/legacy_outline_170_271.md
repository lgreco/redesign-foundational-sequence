# The Legacy Sequence, As Actually Taught: COMP 170 + COMP 271, Summer 2026

## What this document is

A week-by-week record of what COMP 170 and COMP 271 actually covered in the Summer 2026 term — reconstructed from class transcripts, weekly plans, weekly reviews, code artifacts, and the two end-of-term reflections (`comp170su26/improvements.md`, `comp271su26/improvements.md`). Those source folders (`comp170su26/`, `comp271su26/`, `recording_transcripts/`) have since been removed from this repository; this document is what survives them, written specifically to give the COMP 158/159 design team a ground-truth baseline of the sequence being replaced — not the syllabus on paper (that is `topics-141-163-170.md`'s job), but the sequence as it was actually lived in a room with students, including the parts that didn't go as planned.

Both courses ran 11 compressed weeks (not a standard 15-week semester) and were taught synchronously, COMP 271 at 10:25–11:15 AM and COMP 170 at 11:30 AM–12:20 PM, immediately back to back, by the same instructor. GitHub was the primary material channel for both; Sakai was used only for homework exchange. Two companion documents already exist and are not duplicated here in full: `comp170su26/week99/15-week-outline.md` and `comp271su26/week99/15-week-outline.md` repace this same content across 15 weeks with an added linux/system and math thread in every week — read those for the fully elaborated reading citations and the linux/math side-threads this document only summarizes. This document's job is different: it is the flat, chronological record of what happened, in both courses, side by side, as raw material for redesigning the sequence from scratch rather than repacing it.

**A note on terminology.** Following this repository's standing convention, "method" is used throughout for callable code, except where quoting an actual Python built-in name (`print()`) or where the class genuinely taught a bare, non-OOP `def` as a standalone function (COMP 271's `pasta_recipe()` in week 1, before any class exists to hang a method off of).

## Part I — COMP 170 (Introductory Programming, Python), Weeks 1–11

COMP 170 organized its eleven weeks around four recurring pillars — strings, `if` statements, loops, and arrays (lists) — combined in increasingly sophisticated ways, closing with a testing unit and a file-I/O/dictionary capstone. The course opened with an explicit framing that shaped everything after it: in any white-collar technical role, most working time goes to reading and writing about work, not to writing code from scratch, so the course treated programming as a writing-intensive discipline in both formal (Python) and natural (English) language.

### Week 1 — The Shell, Vim, and Your First Program

Bash fundamentals (`pwd`, `ls`, `mkdir`, `cd`) and Vim's two-mode model (`i` / `Esc`, `:w`, `:q`, `:wq`) as the entire toolchain — no IDE. `python3 file.py`, `print()`, comments, and the edit–save–run loop as the atomic unit of programming work. Variables and multi-line output. A deliberate syntax error (`SyntaxError: '(' was never closed`) introduced on purpose to establish that error messages are informative, not hostile. Closed with data types (`str`, `int`, `float`), `type()`, and the distinction between `+` as string concatenation versus numeric addition.

### Week 2 — Compound Interest and Separation of Concerns

Arithmetic operators and precedence, `/` vs. `//` vs. `%`, `input()` and its always-string return type, `int()`/`float()` conversion. Built a compound interest calculator, `interest.py`, then refactored it into `interest_pro.py` — three methods (`read_inputs`, `compute_future_value`, `show_result`), each with exactly one job, collapsing the main program to three lines. This is the course's first and defining statement of **separation of concerns** (input / logic / output), reinforced with a coffee-shop analogy for what a method is (you name the drink; you don't recite the recipe every time) and a brief history of the concept's names across decades (procedure → subroutine → function/method). F-strings (`f"${total:,.2f}"`) introduced for formatted output.

### Week 3 — ASCII, Number Systems, and Loops

`ord()`/`chr()`, four ASCII anchor values worth memorizing (32 space, 48 `'0'`, 65 `'A'`, 97 `'a'`), string repetition (`*`) as conceptually distinct from arithmetic multiplication. Positional number systems — decimal, binary, hexadecimal — converted by hand, with the historical aside that uppercase ASCII values are lower than lowercase because early computers only had memory for uppercase. `for` loops and `range()` built from first principles via ASCII-art shape drawing (staircases, triangles, diamonds, bar charts), always pattern-first: work out the row-by-row rule on paper before writing a line of code. Scope introduced through indentation.

### Week 4 — Conditionals, Booleans, and the Airplane-Seating Problem

`if`/`elif`/`else`, comparison operators, `==` vs. `=`, `and`/`or`/`not` with truth tables (plus a brief look at XOR and NAND). The modulo operator as the week's throughline: even/odd checks, then the airplane-seating problem — converting a flat passenger index into a row/seat label using `//` and `%` together (`chr(65 + passenger % seats_per_row)` for the seat letter, `passenger // seats_per_row + 1` for the row). Students compared their hand-derived solution against Claude's AI-generated version, which used a nested loop and list iteration — concepts not yet covered — making the point that understanding the underlying math is what lets you evaluate AI-generated code rather than merely receive it.

### Week 5 — Lists, the Cumulative Pattern, and String Methods

Lists as a contiguous, indexed collection (apartment-building analogy: every unit the same size, reachable by counting doors, versus 100 people scattered across separate hotels). Zero-based indexing grounded concretely: your position equals how many people are ahead of you. The **cumulative algorithm** (initialize a sum, loop, divide at the end) built by contrasting a hard-coded denominator against one computed with `len()`. Then string methods as the bridge from a single string to a list of words: `.split()`, `.lower()`/`.upper()`, `.strip()`, chained method calls, and `list.append()` as the filter pattern — the same accumulator idea as the cumulative average, now collecting items instead of a number. The recurring worked problem all week: extract every word over $N$ characters from a sentence, uppercase them, and collect the results.

### Week 6 — Packaging Logic into Methods

Wrapped the week 5 filtering logic into a method (`filter_words`) with type hints and a docstring — Python doesn't enforce type hints, but they communicate intent. Input validation introduced as a habit (reject an empty sentence or an unreasonable cutoff length), motivated by a real story about an airline web form that didn't validate age fields, producing thousands of "11111" entries. Running code across files via `import` and `if __name__ == "__main__":`. Loop-variable naming (any name works; a *readable* name is a courtesy to the reader, not a requirement of the language). The **accumulator pattern** generalized from sums to products via factorial, computed first iteratively, then rewritten recursively (`n! = n * (n-1)!`, base case `0! = 1`) — the course's first, brief touch of recursion, arrived at almost incidentally rather than as a planned unit.

### Week 7 — Searching From Scratch: `find`, `index`, and Fixing a Real Bug

`str.find()` vs. `str.index()`: both locate a character, but `.find()` returns $-1$ on failure while `.index()` raises and crashes — a deliberate design choice worth naming (a promise broken loudly vs. a caller left to decide). Students wrote their own `contains`/`indexOf`, discovering along the way that Python's negative indexing (`"Arlo"[-1]`) makes $-1$ a slightly awkward "not found" sentinel, since it's also a valid index. A hand-built string-splitting method (`our_split`) that walks a sentence character by character shipped with a live, real bug: consecutive spaces produced spurious empty-string entries, fixed with a single `if len(new_entry) > 0` guard — the term's canonical debugging story. Definite vs. indefinite loops distinguished, with infinite-loop causes (`while i > -10` when `i` only increases; forgetting to update the loop variable) demonstrated on purpose.

### Week 8 — Nested Loops, Tuples, and the Birth of Testing

Nested loops introduced via a multiplication table (outer loop picks a number, inner loop runs the products) and then applied to real substring search — finding `"cag"` inside `"Chicago"` — an outer loop trying each candidate start position, an inner loop confirming the full match with early exit the moment one character fails. `positions()`, a method that accumulates *every* match into a list rather than stopping at the first, reinforced why an empty list, not a sentinel like $-1$, is the honest "nothing found" value when the return type is already a list.

A second thread revisited the standalone `quad.py` quadratic-equation script, rewriting it to `return` instead of `print`, which required a real payoff for **tuples**: `(x1, x2)` for real roots, `((re1, im1), (re2, im2))` for complex ones when the discriminant is negative — introducing $i$ and complex numbers along the way. The equation's `a = 0` degenerate case forced a live lesson on guarding a division before it happens, not after it crashes.

The week closed by naming **testing** explicitly for the first time, using no code at all: an ATM's withdrawal screen as a discussion vehicle. Building the list together — withdraw more than the balance, withdraw \$0, withdraw a negative amount, withdraw an amount that isn't a multiple of \$20, the machine itself out of cash — made the point that edge cases don't show up by accident; a tester goes looking for them on purpose, and every one of `solve_quadratic`'s special-cased branches from earlier in the week was already, quietly, that exact exercise.

### Week 9 — Errors, `try`/`except`, and Dictionaries (First Attempt)

Designed `enter_grade` for a GPA tracker from a vague client request ("no course database needed"), converting the ATM's testing habit into real bugs found live: a lowercase letter (`a` instead of `A`) and a mistyped letter both silently scored as zero, fixed first by normalizing case, then by `raise ValueError` for genuinely invalid input — the course's first use of raising an exception deliberately, framed as "crash loudly rather than silently corrupt the GPA." `try`/`except` then closed the loop from the caller's side: a retry loop around `int(input())` that catches `ValueError` and asks again instead of crashing, discussed against a real design tension (some teams prefer to fail fast on bad input; this course leaned toward giving users a chance to recover from an honest typo, drawing an analogy to airline pilots double-checking each other's altitude entries). A planned pivot to dictionaries — replacing `enter_grade`'s `if` chain with a lookup — was drafted in the private plan for this week but **did not happen live**; it would be deferred twice more before finally landing in week 11.

### Week 10 — Memory, Storage, and Files

Opened with a poll asking students how much memory their computers have; most answers described storage capacity instead — the mix-up became the week's hook. Built the memory/storage distinction from scratch rather than from the classic "does it spin" mechanical tell, which no longer works once flash storage has no moving parts either: the real distinction is whether data survives after the program ends and the power is off. A brief history from punched cards to magnetic tape (sequential-only, like a cassette) to spinning disks (random access, like a vinyl needle, vulnerable to head crashes from a speck of dust) to today's electronic storage. The von Neumann three-tier hierarchy (registers, main memory, storage). Then hands-on file operations: `open()` in `"w"`/`"r"`/`"a"` modes, watching a file appear in the folder the instant it's opened, the write buffer (nothing shows up until `.close()`), reading line by line, and `.rstrip()` to fix the double-newline artifact from `print()`. Closed by connecting files back to the four pillars (strings, loops, `if`, lists) and previewing structured formats (CSV, XML, JSON) as what comes after plain text once a flat comma-separated layout starts breaking under new fields.

### Week 11 — The Capstone: Word Frequency, and Dictionaries at Last

The term's final live week, built entirely around one text-analysis capstone: count word frequencies in *A Tale of Two Cities*, first fetched locally, then read a line at a time directly from a URL via `urllib.request` (to avoid loading a whole book into memory at once — the assignment's stated reason for the streaming approach). Two synchronized lists (one of unique words, one of matching counts) were built **deliberately**, named "array synchronization," and explicitly flagged as fragile — the instructor's own framing was that this technique was kept alive only to justify replacing it. Two real bugs surfaced live: an off-by-one error in the synchronized-list search, and an infinite loop from checking for end-of-file the wrong way (an empty line is not the same condition as nothing left to read). The messy inline code was then refactored into two named methods (a lookup returning $-1$ on failure, and an update-or-insert step), shrinking roughly twenty tangled lines to two clean ones — a direct callback to week 7's `indexOf` pattern. Only then were the two lists retired in favor of a single **dictionary**, `{word: count}`, with lookup and update each collapsing to one line. A late bug (`"times,"` vs. `"times"` counted separately because of an attached comma) motivated stripping punctuation before counting. This was dictionaries' only appearance in the entire term — introduced, used once, and the course ended.

## Part II — COMP 271 (Data Structures I, Python), Weeks 1–11

COMP 271 assumed COMP 170's terminal and Vim fluency without re-teaching it, and built one continuous arc: a hand-rolled fixed-capacity array wrapped in a first class, generalized into linked structures, then stacks, queues, recursion, graphs, file-backed structures, and hashing — ending exactly where Python's built-in `dict` begins. Students were nudged toward VS Code or GitHub Codespaces over IDLE from week 1, with the **Black** formatter demonstrated as an example of professional, automated style enforcement.

### Week 1 — Separating Data from Behavior

The **Mississippi progression**: `mississippi.py` (letters hard-coded into individual `print()` calls) → `block_letters.py` → `mississippi_horizontal.py`, which stores each letter as a list of row-strings and prints horizontally with a nested loop (outer over row index, inner over each letter in the word) — the term's first demonstration that data stored as a structure (a list) succeeds where data baked into code cannot. `pasta.py` refactored into `get_guests()` / `pasta_recipe()` / `display_recipe()` / `main()` as a second, non-OOP example of the same separation-of-concerns instinct COMP 170 taught with `interest_pro.py`. No object-oriented content yet — this week's "design" lesson is compositional, not classes.

### Week 2 — Arrays, Objects, and the First Class

True fixed-size, single-type arrays contrasted with Python's dynamic list (which the course treats as an array-substitute throughout, while naming the difference honestly). Classes as blueprints, objects as instances, `__init__`, `self` — introduced with a running joke that `self` is just a parameter name (demonstrated live by renaming it to students' least-favorite vegetables) rather than a reserved keyword, unlike Java's compiler-enforced `this`. Built the first `DynamicArray`: four sentinel `-1` slots and `add_zip_code()`, tested interactively by filling all four slots and confirming a fifth addition is correctly rejected. Closed with an ungraded weekend challenge — double a four-element list's size in plain Python, no `def`, no `class`, no `.append()` — that became week 3's opening move.

### Week 3 — Resizing, Magic Numbers, and a Real Debugging Story

Walked the doubling operation by hand as flat, procedural code before wrapping anything in a class: allocate double, copy with `range(size)` (not `range(capacity)` — copy only what's real), reassign. Then wrapped `resize()`/`add()` as standalone functions, surfacing the "three-variable problem" — a caller has to carry `data`, `size`, and `capacity` everywhere and nothing stops them from passing mismatched values — as the direct, felt motivation for a class (this bridges straight into week 4). Percentage-based resizing was floated as an alternative to doubling and produced the term's signature bug: `int(3 * 1.1)` truncates to `3`, silently failing to grow the array at all. Diagnosed live and fixed with `math.ceil()` instead of `int()` — the course's canonical illustration of floor vs. ceiling rounding and why "always round up" is correct whenever the rounded value is a required minimum, not an estimate. Amortized cost (doubling is rare but the average cost per add stays constant) named as an intuition, explicitly deferred from formal analysis.

### Week 4 — Dunder Methods, Bounds Checking, and Structured Programming

`__str__` and `__len__` as dunder ("special") methods Python wires to built-in behavior — demonstrated by temporarily removing `__str__` and watching `print()` fall back to a raw memory address. The negative-index trap in `get()` (Python treats $-1$ as "last element," so a naive bounds check silently accepts what should be rejected) and its `index >= 0` fix. `contains()` refactored to delegate to `index_of()` rather than duplicating a full scan — named explicitly as "eliminate redundancy by delegating to methods that already do the work." The shift-and-clear `remove()` algorithm, designed step by step before any code was written. A structured-programming principle was named directly in this stretch: Dijkstra's single-entry/single-exit rule, with `break` called out as "a disguised `goto`" — the stated reason `index_of` is written with a `while` loop whose own condition encodes both "not found" and "not exhausted," rather than a `for` loop with an early `break`.

### Week 5 — Contracts, Composition, and the First Linked Node

Introduced the **contract** concept: every data structure the course builds will expose at least `contains`, `index_of`, `index_of_all`, `count`, and `remove` — implemented formally as a Python abstract base class (`ABC`, `@abstractmethod`), with the explicit note that a class can technically satisfy a contract's method signatures while missing its spirit; docstrings on the abstract methods are how that spirit gets communicated. `FellowshipRoster` built as **composition** ("has a" `DynamicArray`) rather than inheritance. Magic values named and replaced with constants; `str.join()` preferred over repeated string concatenation, backed by a live memory demonstration — growing a string by repeated concatenation changes its memory address every time (strings are immutable), and doubling a string's length across ~30 iterations crashes with a memory error well before reaching astronomically large sizes. Closed with `station.py`: the term's first class whose own field points to another instance of the same class — the direct prerequisite for every linked structure that follows.

### Week 6 — Linked Traversal, Tail Pointers, and Big O

Built a `TrainLine` on top of `Station` using the CTA Red Line as a running metaphor. Adding a station without a tail pointer costs a full traversal from the head — an $\mathcal{O}(n)$ operation named and felt before it was formalized — motivating a `_tail` field that brings `add()` to $\mathcal{O}(1)$. Big O formalized as an upper bound ($f(n) \in \mathcal{O}(g(n))$ when $f(n) \le c \cdot g(n)$) and contrasted with Big Theta as a tight bound, alongside the rice-on-a-chessboard and museum-heist examples for exponential and factorial growth, and a concrete comparison at $n=100$ ($n^2 = 10{,}000$ vs. $2^{100} \approx 10^{30}$, longer than the age of the universe in seconds). A live infinite-loop bug — `cursor.get_next()` called but never reassigned back to `cursor` — became the term's canonical iteration bug, fixed and then generalized into a proper `__iter__` using `yield`, distinguished from `return` as "resumes instead of exiting."

### Week 7 — Generic Nodes and a Doubly Linked List

Generalized `Node` with `TypeVar`/`Generic` so a payload can be any type, and demonstrated live that Python's type hints are purely advisory — two `Node`s with different payload types coexist without error, unlike Java, where the equivalent generic notation is compiler-enforced (a recurring point of comparison, since COMP 272 is taught in Java). Built `DoubleLinkedList` with a `bidirectional` constructor flag, so the same class can also model a unidirectional structure by simply never setting `_previous`. The **slow/fast cursor** technique for finding a list's middle node in one pass, reasoned out as a staircase argument (the slow cursor is at position $\lfloor n/2 \rfloor$ exactly when the fast one reaches the end), backed by a maintained node-count field so the middle position is always known without a preliminary counting pass. List reversal solved by rewiring both `next` and `previous` pointers in a single traversal using a temporary reference, worked out first on a whiteboard with students physically pointing at each other. $O(1)$ removal at either end (three pointer reassignments, with the single-node case as the branch most often gotten wrong) and $O(1)$ cycle/discontinuity detection by checking only `head._prev` and `tail._next` for `None` — proven correct by the invariant that `add()` is the only method that ever sets pointers, so those two positions are the only ones that can ever legitimately be `None`.

### Week 8 — Stacks, Queues, and Abstract Data Types

With head/tail removal now in place, built `Stack` (LIFO, `push`/`pop` both at the tail) and `Queue` (FIFO, `enqueue` at the tail, `dequeue` at the head) as thin, composition-based wrappers around `DoubleLinkedList` — every operation $\mathcal{O}(1)$, the direct payoff of the tail-tracking work from week 6. Then stepped back to name what had just been built: an **abstract data type** is a specification of behavior, independent of implementation — the same idea as week 5's contract, under its formal name, made concrete by sketching a second `Stack` implementation backed by a plain Python `list` instead of a linked list and asking whether calling code could tell the two apart (it can't). Connected forward explicitly to COMP 272: Java's `Queue`/`Deque` interfaces with multiple implementing classes (`LinkedList`, `ArrayDeque`) are the same idea in different syntax.

### Week 9 — Circular Buffers and Graphs

Array-based stacks and queues surfaced a real shifting bug: shifting elements right with a left-to-right loop propagates one value across the whole array instead of moving each value once, fixed by reversing the loop direction (`range(size-1, -1, -1)`). Circular arrays resolved the underlying cost problem by replacing shifts with two pointers (`front`, `back`) advancing via `(position + 1) % capacity`, tying directly to periodic boundary conditions (clocks, 24-hour time) and to Python's own negative-index wraparound behavior. Time complexity compared directly: array-backed queue insertion is $\mathcal{O}(1)$ but removal $\mathcal{O}(n)$; a stack backed by the same array is $\mathcal{O}(n)$ for both; a linked-list version is $\mathcal{O}(1)$ for everything, at the cost of per-node memory overhead. Pivoted into graphs: vertices and edges via a plain-English "can you reach town H from town A" framing, the adjacency list representation (each vertex's own list of neighbors), then the adjacency matrix (an $n \times n$ symmetric array with a zero diagonal for an undirected graph), and a first, naive reachability traversal that visits every reachable vertex before ever checking whether the target was among them — deliberately left inefficient, since fixing that inefficiency became the following week's assignment.

### Week 10 — File-Backed Structures

An async, non-live Monday assigned LeetCode problems plus a genuinely open design question: could a queue or stack be built using file operations only, no in-memory lists or arrays? Two live sessions then designed exactly that: an empty queue as a zero-byte file, one item per line, `enqueue()` as an append, and `dequeue()` — the hard case, since a plain text file has no way to delete just its first line — solved by copying every remaining line into a temporary file and swapping it in. Named constants replaced hard-coded file names and capacities, with a side excursion into Java's compiler-enforced `final` (demonstrated live) versus Python's complete absence of such enforcement — constants here are convention, "the we are all adults here principle," not a guarantee. A companion assignment pushed the same idea further: a fully file-backed doubly linked list, two head/tail anchor files, randomly named intermediate node files, and a name-collision check against a directory of files already in use — which became the direct, felt motivation for week 11's turn toward hashing (estimating how likely two 8-character random file names are to collide is exactly the pigeonhole-principle question hashing exists to answer).

### Week 11 — Hashing, and the Term's Final Assignment

The term's last synchronous week, built as one continuous narrative rather than a list of separate topics. Opened by connecting the week 10 file-collision problem to the need for fast lookup: a linear scan is $\mathcal{O}(n)$; binary search on a sorted list is $\mathcal{O}(\log n)$ but costs $\mathcal{O}(n \log n)$ to sort first; the question that remains is whether $\mathcal{O}(1)$ lookup is possible at all. Answered with a hotel-room hashing metaphor: assign each guest a room by the first letter of their last name for $\mathcal{O}(1)$ lookup, at the cost of wasted rooms and collisions (two real student surnames sharing a first letter became the class's own collision example). Linear probing tried first and shown to degrade quickly as more keys collide; chaining introduced next and explicitly recognized as "an array of the linked lists we already built" in week 7 — reusing, rather than reintroducing, the term's core node-and-pointer vocabulary. Weak hash functions demonstrated empirically: summing or multiplying ASCII codes produces predictable periodicities (most products come out even, since half the alphabet has an even ASCII value); `abs()` on a hash code guards against integer-overflow wraparound. Load factor $\alpha = \frac{\text{slots used}}{\text{capacity}}$ named as the single number governing expected chain length, with resize-and-rehash triggered once occupancy passes roughly 75%. Closed by naming Python's `dict` as exactly this structure, "a key-value store nobody should reimplement by hand" — and then assigning students to do exactly that, in `SimpleHash`, the term's final assignment.

## Cross-Sequence Synthesis

### What COMP 271 assumes COMP 170 already built

| COMP 271 week 1–2 assumption | Where COMP 170 built it |
|---|---|
| Terminal and Vim fluency, no re-teaching | Week 1 |
| Separation of concerns (input/logic/output as distinct methods) | Week 2 (`interest_pro.py`) |
| A method with a docstring and type hints | Week 6 (`filter_words`) |
| Comfort with lists as the working stand-in for arrays | Week 5 |
| A single class with a constructor and `self` | *(gap — see below)* |

That last row is the seam the two courses actually share weakly, not strongly: COMP 170 ends with strings, loops, `if`, arrays, exceptions, and one dictionary, but never writes a `class`. COMP 271 opens week 2 introducing `__init__` and `self` as though for the first time, because — from the data available — it effectively is. This matches `topics-141-163-170.md`'s gap analysis almost exactly, written before this term ran and confirmed by how the term actually went: COMP 170 never reaches OOP, so COMP 271 has to spend part of its own week 2 on material a well-sequenced COMP 170 could have already covered.

### The two courses' internal arcs, side by side

| | COMP 170 | COMP 271 |
|---|---|---|
| Weeks 1–2 | Shell, Vim, first program, types, separation of concerns | Mississippi/pasta refactors, arrays vs. lists, first class |
| Weeks 3–5 | ASCII, number systems, loops, conditionals, lists, string methods | Resizing, magic numbers, the `math.ceil()` bug, dunders, contracts |
| Weeks 6–8 | Methods, recursion (brief), nested loops, tuples, testing named | Linked traversal, Big O, generic nodes, doubly linked lists |
| Weeks 9–11 | `try`/`except`, files, dictionaries (once, at the very end) | Stacks/queues/ADTs, circular buffers, graphs, file-backed structures, hashing |

Read this way, the two courses are not sequential halves of one story so much as two separate arcs that happen to run in the same term: COMP 170 spends its second half on defensive programming and I/O, while COMP 271 spends its second half on data structures and complexity — and the handoff between them (OOP, recursion, dictionaries) is exactly the material both end-of-term reflections flag as thin, late, or missing.

### Known gaps, confirmed by this term's actual delivery

Everything below is corroborated by what's documented above, not just asserted in the reflections that originally named it:

- **Dictionaries arrived once, in the last week of COMP 170, and were never revisited.** The week 9 plan intended to teach them earlier; the actual week 9 and week 10 sessions both pivoted away (to `try`/`except`, then to files) before dictionaries finally landed in week 11 as part of the capstone. Students got the payoff of "a dictionary beats two synchronized lists" without the repetition needed to make it stick.
- **OOP is a real seam, not a soft one.** COMP 170 never writes a `class`; COMP 271 introduces one in its second week. Inheritance and polymorphism — which COMP 271's own contract-based design (`ABC`, abstract methods) leans on structurally — never appear in COMP 170 at all.
- **Recursion appears exactly twice, both briefly.** Once in COMP 170 week 6 (factorial, almost as an aside to the accumulator pattern) and once in COMP 271 week 10 (factorial again, pushed to a `RecursionError` on purpose as a bridge to the call stack). Neither course builds a second recursive example on top of the first.
- **No sorting algorithm was ever implemented in COMP 271**, despite eleven weeks of array and linked-structure work that builds exactly the scaffolding a sort needs.
- **Trees never appeared**, despite the `Node`-with-one-pointer vocabulary being one field short of a `TreeNode` since week 7.
- **Testing was named as a concept (COMP 170 week 8's ATM discussion) well before it was practiced as a habit.** Both courses treat testing as something demonstrated in a dedicated stretch — COMP 170's week 8/13 quadratic-equation unit, COMP 271's expected-output comments checked by eye — rather than something students do to their own code from week 1 onward.
- **Git was used constantly and taught never.** Every assignment in both courses lived in a git-hosted repository; neither course ever covered `git add`/`commit`/`status` as content.

These six gaps are the same ones independently named in `comp170su26/improvements.md`, `comp271su26/improvements.md`, and `topics-141-163-170.md`'s syllabus-based gap analysis — three different vantage points (a live-term reflection for each course, and a paper-syllabus review done before the term ran) converging on the same list. That convergence is itself evidence: these are not artifacts of one bad week or one instructor's blind spot, but structural gaps in how the legacy sequence is shaped, worth treating as load-bearing constraints on the COMP 158/159 design rather than incidental fixes.

### What worked well enough to preserve deliberately

- **The recurring problem, not the recurring lecture.** Both courses' strongest weeks (COMP 170's word-filtering problem spanning weeks 5–6; COMP 271's `DynamicArray` spanning weeks 2–6) kept one concrete problem on screen across multiple sessions and added machinery to it incrementally, rather than introducing a new toy example every day.
- **Bugs used as the teaching device, not edited out.** The `math.ceil()` resize bug, the consecutive-delimiter `split()` bug, the `cursor.get_next()` infinite loop, and the off-by-one in the word-counting capstone were all left in, diagnosed live, and referenced again in later sessions — each became a shared reference point ("the same mistake as the resize bug") rather than a one-off fix.
- **Reframing formal ideas through non-code analogies before code.** The ATM's edge-case list for testing, the hotel-room metaphor for hashing, the whiteboard/notebook distinction for memory vs. storage, and the CTA Red Line for linked traversal all did real conceptual work before any Python was written.
- **Naming the connection to COMP 272 (Java) explicitly and often**, rather than leaving the Python-to-Java transition implicit — dunder methods vs. Java's enforced `this`, Python's advisory type hints vs. Java's compiler-enforced generics, and Java's `Queue`/`Deque` interfaces as the same ADT idea COMP 271 built with `ABC`.
